## 2. Термины, определения и сокращения, используемые в техническом задании

Для целей настоящего технического задания используются следующие термины и их определения:
**Ритм-игра (ритмическое взаимодействие) —** жанр компьютерных видеоигр, в котором ключевой игровой процесс базируется на синхронизации физических действий игрока по нажатию клавиш ввода с воспроизводимым музыкальным рядом и перемещением графических объектов.
**Игровая нота (нота) —** интерактивный графический элемент, формируемый на игровом поле и движущийся по горизонтальной направляющей к линии зоны нажатия, требующий нажатия назначенной клавиши в заданный момент времени.
**Игровая карта (карта, битмап) —** структурированный пакет данных, содержащий файл аудиокомпозиции, метаданные композиции, упорядоченный по времени массив нот, параметры скорости прокрутки и графический файл обложки.
**Файл формата .bkey —** специализированный файл-контейнер на базе формата ZIP, объединяющий файл разметки нот (map.json), аудиофайл композиции и изображение обложки.
**Таблица лидеров (рейтинг) —** подсистема учета и отображения результатов игроков по выбранной карте, функционирующая на базе облачной базы данных Firebase Realtime Database.
**Встроенный редактор карт —** программный модуль Системы, предназначенный для создания, разметки, редактирования и тестирования игровых карт.
**Окно регистрации (тайминг-окно) —** допустимый временной интервал относительно целевого момента удара ноты, в пределах которого нажатие клавиши регистрируется Системой с присвоением одной из четырех градаций точности.
**Зона нажатия (линия регистрации) —** графическая контрольная область на игровом экране, при совмещении ноты с которой производится нажатие клавиши.
**Аудио-офсет (калибровка задержки) —** программная компенсация задержек звукового тракта и устройств ввода путем сдвига шкалы регистрации нот в миллисекундах.
**Профиль игрока —** идентификационные данные пользователя (псевдоним длиной от 3 до 20 символов), используемые для отображения в интерфейсе и сохранения рекордов в таблице лидеров.
**Qt —** кроссплатформенный фреймворк и набор библиотек для разработки программного обеспечения на языке C++.
**Firebase Realtime Database —** облачная NoSQL база данных, обеспечивающая удаленное хранение и выборку данных в формате JSON по протоколу HTTPS через REST API.
**Комбо (Combo) —** непрерывная серия успешных нажатий («Идеально», «Хорошо», «Сойдет») без пропусков и штрафных нажатий.
**Шкала здоровья (HP, Health Points) —** числовой показатель запаса прочности игрока в диапазоне от 0 до 100 единиц, определяющий возможность продолжения игрового раунда.
**Хеш карты (Map Hash) —** 64-символьная шестнадцатеричная строка, рассчитанная по алгоритму SHA-256 от массива байтов файла map.json и аудиофайла карты.
В настоящем техническом задании приняты следующие сокращения:
* ПО — программное обеспечение;
* ОС — операционная система;
* БД — база данных;
* API — Application Programming Interface (интерфейс прикладного программирования);
* GUI — Graphical User Interface (графический интерфейс пользователя);
* BPM — Beats Per Minute (темп музыкального произведения в ударах в минуту);
* FPS — Frames Per Second (частота смены кадров в секунду);
* REST — Representational State Transfer (архитектурный стиль клиент-серверного взаимодействия);
* JSON — JavaScript Object Notation (текстовый формат обмена данными);
* SHA — Secure Hash Algorithm (криптографический алгоритм хеширования);
* HUD — Heads-Up Display (информационная панель поверх игрового поля);
* RAM — Random Access Memory (оперативная память).

## 3. Назначение и цели создания системы

### 3.1. Цели и задачи разработки:

**3.1.1.** разработка игрового программного обеспечения ритмического взаимодействия «BeatKey», поставляемого в виде автономного исполняемого файла (.exe) для персональных компьютеров под управлением ОС Windows (Windows 10, Windows 11);
**3.1.2.** реализация игровой механики взаимодействия с нотами в такт воспроизводимой музыке с частотой обновления кадров не менее 60 кадров/с;
**3.1.3.** создание формата хранения игровых уровней (.bkey);
**3.1.4.** разработка встроенного визуального редактора карт, позволяющего пользователям создавать и настраивать авторские музыкальные уровни без использования стороннего программного обеспечения;
**3.1.5.** интеграция с базой данных Firebase Realtime Database для ведения глобальной таблицы лидеров с сохранением рекордов под выбранным именем пользователя;
**3.1.6.** реализация детерминированной системы оценки точности нажатий, серий комбо и подсчета очков с градацией мастерства прохождения;
**3.1.7.** обеспечение калибровки задержки ввода (аудио-офсета) и синхронизации графического ряда с воспроизводимым звуковым потоком;
**3.1.8.** создание графического интерфейса пользователя с функциями настройки звука, видеорежима и управления.

### 3.2. Автоматизация процессов:

**3.2.1.** автоматизация импорта, проверки целостности и разбора структуры файлов карт формата .bkey;
**3.2.2.** автоматизация синхронизации позиций движущихся нот на экране с текущей позицией воспроизведения аудиокомпозиции на базе таймера QElapsedTimer;
**3.2.3.** автоматизация регистрации нажатий клавиш ввода и их классификации по четырем фиксированным градациям точности попадания в ритм («Идеально», «Хорошо», «Сойдет», «Промах»);
**3.2.4.** автоматизация вычисления итогового счета, максимальной серии комбо, процента точности и статуса завершения игры (победа или поражение);
**3.2.5.** автоматизация отправки результатов сессии в базу данных Firebase Realtime Database и загрузки актуальной таблицы лидеров по выбранной карте;
**3.2.6.** автоматизация создания, валидации и экспорта пользовательских карт во встроенном редакторе.

## 4. Требования к системе

### 4.1. Требования к системе в целом

**4.1.1.** Система должна быть реализована в виде самостоятельного настольного приложения для ОС Windows (Windows 10, Windows 11 64-bit), функционирующего без необходимости установки сторонних сред выполнения.
**4.1.2.** Прикладное программное обеспечение должно разрабатываться по модульному принципу, обеспечивающему разделение логики предметной области, рендеринга, звукового сопровождения, сетевого взаимодействия и интерфейса пользователя.
**4.1.3.** Система разрабатывается на языке программирования C++ (стандарт C++20) с применением библиотеки и фреймворка Qt 6. Графический интерфейс, мультимедийная подсистема воспроизведения звука, таймеры синхронизации и сетевое взаимодействие реализуются с использованием официального API Qt. В проекте используются следующие модули библиотеки Qt:
**4.1.3.1. Модуль QtCore:** используется для базовых структур данных и контейнеров, реализации объектной модели Qt, механизмов сигналов и слотов для межкомпонентного взаимодействия без жестких зависимостей, управления жизненным циклом объектов, а также применения высокоточного таймера QElapsedTimer для отсчета времени игрового раунда в миллисекундах;
**4.1.3.2. Модуль QtGui:** используется для базовых графических примитивов (QPainter, QColor, QPixmap) и низкоуровневой обработки событий клавиатурного ввода QKeyEvent с обязательной фильтрацией системного автоповтора удерживаемых клавиш;
**4.1.3.3. Модуль QtWidgets:** используется для построения экранных форм графического интерфейса (QMainWindow), элементов управления (кнопки QPushButton, ползунки QSlider, текстовые поля QLineEdit, выпадающие списки QComboBox), таблиц рейтинга (QTableWidget), диалоговых окон подтверждения (QMessageBox) и компоновщиков разметки (QLayout);
**4.1.3.4. Модуль QtMultimedia:** используется для декодирования и воспроизведения аудиофайлов музыкальных композиций (классы QMediaPlayer, QAudioOutput) с позиционированием аудиодорожки по миллисекундной шкале, а также для воспроизведения звуковых эффектов попадания (hit.wav) и промаха (miss.wav) через QSoundEffect с задержкой не более 10 мс;
**4.1.3.5. Модуль QtNetwork:** используется для асинхронного сетевого взаимодействия по протоколу HTTPS через REST API базы данных Firebase Realtime Database (классы QNetworkAccessManager, QNetworkRequest, QNetworkReply), а также для сериализации и разбора JSON-пакетов средствами классов QJsonDocument, QJsonObject, QJsonArray.
**4.1.4.** В Системе должна быть предусмотрена независимость подсистемы загрузки и хранения карт от внешних сетевых подключений: при отсутствии соединения с сетью Интернет игровой процесс и редактор карт должны сохранять полную функциональность в локальном автономном режиме.
**4.1.5.** Архитектура Системы должна обеспечивать возможность добавления новых музыкальных карт, графических элементов оформления и модификации алгоритмов подсчета очков без изменения программного ядра приложения.
**4.1.6.** Программа должна обеспечивать обработку исключительных ситуаций (отсутствие звуковых устройств, повреждение файлов данных, сетевые таймауты) без аварийного завершения работы приложения.
**4.1.7.** Система должна предоставлять текстовые информационные сообщения пользователю в случае возникновения ошибок загрузки или сетевого обмена.

### 4.2. Требования к функционированию

**4.2.1.** Доступ ко всем функциональным режимам Системы должен осуществляться через единый графический интерфейс.
**4.2.2.** При запуске программы Система должна открывать экран Главного меню, содержащий логотип «BeatKey» и четыре кнопки управления:

**1)** Кнопка «Играть» — переводит Систему на экран выбора карты (п. 4.2.3);

**2)** Кнопка «Редактор» — переводит Систему в режим встроенного визуального редактора карт (п. 4.9);

**3)** Кнопка «Настройки» — открывает экран параметров Системы, калибровки задержки звука и конфигурации клавиш (п. 4.11);

**4)** Кнопка «Выход» — открывает модальное диалоговое окно подтверждения выхода с текстом «Вы уверены, что хотите выйти из игры?» и двумя кнопками: «Да» и «Нет». При нажатии кнопки «Да» Система освобождает выделенные ресурсы и завершает процесс приложения. При нажатии кнопки «Нет» диалоговое окно закрывается, фокус возвращается в Главное меню.
**4.2.3.** Экран выбора карты должен содержать следующие элементы:
* вертикальный список доступных карт формата .bkey, обнаруженных в локальном каталоге ./maps/, с отображением названия трека, исполнителя, автора карты, уровня сложности и темпа BPM;
* графическую область отображения обложки выбранной карты (cover.png);
* подсистему аудио-предпросмотра: при выборе карты из списка Система автоматически запускает воспроизведение фрагмента трека длительностью 15 секунд с временной позиции previewTimeMs, указанной в манифесте карты;
* панель таблицы лидеров по выбранной карте с двумя переключаемыми вкладками: вкладка «Локальный рейтинг» (отображает таблицу из 10 лучших результатов, сохраненных на локальном компьютере) и вкладка «Глобальный рейтинг» (отображает таблицу из 10 лучших результатов, загруженных из сетевой базы данных Firebase Realtime Database);
* кнопку «Старт» — инициирует загрузку и запуск игрового процесса по выбранной карте;
* кнопку «Назад» — возвращает пользователя в Главное меню.
**4.2.4.** В процессе игрового раунда Система должна обеспечивать возможность приостановки игры (пауза) по нажатию клавиши Escape с выводом меню паузы («Продолжить», «Начать заново», «Выход в меню»), возобновления, перезапуска карты за время не более 1000 мс и досрочного выхода в экран выбора карт.
**4.2.5.** При потере соединения с сервером базы данных Система должна переходить в автономный режим, сохраняя локальный результат сессии и информируя пользователя сообщением в строке статуса.
**4.2.6.** Система должна автоматически сохранять и восстанавливать пользовательские настройки между сеансами работы (уровни громкости, калибровка офсета, видеорежим, привязки клавиш, имя игрока) в конфигурационном файле settings.ini.
**4.2.7.** Система должна выполнять валидацию файлов карт при добавлении в библиотеку, исключая зависание и сбой программы при наличии некорректных или поврежденных данных.

### 4.3. Требования к навигации

**4.3.1.** Навигация между экранами и разделами Системы должна быть однозначной и единообразной во всех режимах.
**4.3.2.** Возврат на предыдущий экран или в Главное меню должен выполняться нажатием кнопки «Назад» графического интерфейса либо нажатием стандартной клавиши отмены Escape.
**4.3.3.** В интерфейсе должно поддерживаться управление как с использованием манипулятора «мышь», так и посредством клавиатурных комбинаций для основных действий: выбор пунктов меню, подтверждение выбора клавишей Enter, отмена действия клавишей Escape.
**4.3.4.** На экранах выбора карты и настроек должно отображаться текущее состояние выбранных параметров и активный псевдоним игрока.
**4.3.5.** В Системе должны отсутствовать тупиковые состояния интерфейса, исключающие возможность возврата или отмены действия.

### 4.7. Требования к разделу «Игровой процесс»

#### 4.7.1. Жизненный цикл игрового процесса

**4.7.1.1. Старт раунда:** раунд начинается при нажатии кнопки «Старт» на экране выбора карты. Система загружает аудиофайл и разметку нот в оперативную память, сбрасывает счетчики (Score = 0, Combo = 0, MaxCombo = 0, N_300 = 0, N_200 = 0, N_100 = 0, N_miss = 0), устанавливает уровень здоровья HP = 50 единиц и начинает воспроизведение композиции с отметки 0 мс;
**4.7.1.2. Вступительный период:** отрезок времени от 0 мс до момента t = t_первая_нота - 100 мс (за 100 мс до момента удара первой ноты карты). В течение вступительного периода нажатия назначенных игровых клавиш игнорируются Системой, штрафные очки не начисляются, уровень здоровья HP не снижается;
**4.7.1.3. Движение нот:** каждая нота появляется на правой границе игровой дорожки за 1000 мс (время долета Travel Time = 1000 мс) до целевой временной отметки t_ноты и движется горизонтально справа налево с постоянной скоростью к фиксированной зоне нажатия, расположенной в левой части экрана. Частота обновления кадров рендеринга составляет не менее 60 кадров/с на базе таймера QElapsedTimer.

#### 4.7.2. Управление игровым процессом

**4.7.2.1.** удары по нотам выполняются двумя назначенными клавишами: Основной (Primary Key) и Дополнительной (Secondary Key). По умолчанию назначены клавиши Z и X. Клавиши могут нажиматься поочередно либо одновременно;
**4.7.2.2.** Система производит программную фильтрацию автоповтора клавиш операционной системы (event->isAutoRepeat() == false). Удержание клавиши не порождает повторных ударов. Для каждого удара требуется отдельное физическое нажатие клавиши.

#### 4.7.3. Окна точности (тайминг-окна) и классификация попаданий. При нажатии назначенной клавиши вне вступительного периода Система рассчитывает абсолютную временную погрешность: |Δt| = |t_воспроизведения - t_ноты|, где t_воспроизведения — текущее время воспроизведения аудиокомпозиции в миллисекундах с учетом Audio Offset, t_ноты — целевое время удара ноты. Система классифицирует действие по четырем фиксированным градациям:

**1)** «Идеально» (категория 300): |Δt| <= 25 мс. Базовые очки: BaseScore = 300. Изменение уровня здоровья: прибавление 2 единиц (HP = min(100, HP + 2)). Серия комбо увеличивается на 1 (Combo = Combo + 1). Воспроизводится звуковой эффект hit.wav. На экране отображается всплывающий маркер «ИДЕАЛЬНО». Счетчик N_300 увеличивается на 1;

**2)** «Хорошо» (категория 200): 25 мс < |Δt| <= 50 мс. Базовые очки: BaseScore = 200. Изменение уровня здоровья: прибавление 1 единицы (HP = min(100, HP + 1)). Серия комбо увеличивается на 1 (Combo = Combo + 1). Воспроизводится звуковой эффект hit.wav. На экране отображается всплывающий маркер «ХОРОШО». Счетчик N_200 увеличивается на 1;

**3)** «Сойдет» (категория 100): 50 мс < |Δt| <= 100 мс. Базовые очки: BaseScore = 100. Изменение уровня здоровья: 0 единиц (уровень HP не изменяется). Серия комбо увеличивается на 1 (Combo = Combo + 1). Воспроизводится звуковой эффект hit.wav. На экране отображается всплывающий маркер «СОЙДЕТ». Счетчик N_100 увеличивается на 1;

**4)** «Промах» (категория 0 / Miss): фиксируется в двух случаях: при нажатии назначенной клавиши, когда |Δt| > 100 мс относительно ближайшей ноты, либо при автоматическом улете ноты за зону нажатия более чем на 120 мс (t_воспроизведения - t_ноты > 120 мс) без нажатия клавиши игроком (автопромах). В обоих случаях: базовые очки BaseScore = 0; уровень здоровья снижается на 5 единиц (HP = max(0, HP - 5)); серия комбо сбрасывается в 0 (Combo = 0); воспроизводится звуковой эффект miss.wav; на экране отображается маркер «ПРОМАХ»; счетчик N_miss увеличивается на 1.

#### 4.7.4. Обработка перекрытия нот (Note Overlap)

если в пределах окна регистрации (|Δt| <= 100 мс) одновременно находятся две и более несыгранные ноты, единичное нажатие клавиши регистрирует ровно одну ноту — ближайшую к линии зоны нажатия (имеющую наименьшее значение |Δt|). Зарегистрированная нота помечается как сыгранная и исключается из обработки. Вторая нота регистрируется только при следующем отдельном физическом нажатии клавиши ввода.

#### 4.7.5. Защита от спама клавиш (штраф за ложные нажатия)

если пользователь производит нажатие назначенной игровой клавиши вне вступительного периода в момент времени, когда в интервале |Δt| <= 100 мс отсутствует активная нота (спам клавиш), Система фиксирует штрафное ложное нажатие: уровень здоровья снижается на 5 единиц (HP = max(0, HP - 5)); текущая серия комбо сбрасывается в 0 (Combo = 0); воспроизводится звуковой эффект ошибки miss.wav.

#### 4.7.6. Формула начисления очков за попадание (HitScore)

за каждое успешное попадание начисляются очки по формуле: `HitScore = BaseScore * (1 + min(Combo, 100) / 25)`

$$HitScore = BaseScore \times \left(1 + \frac{\min(Combo, 100)}{25}\right)$$

$$TotalScore = \sum HitScore$$

где `BaseScore` — базовые очки категории попадания (300, 200 или 100), `Combo` — текущее значение серии комбо до фиксации текущего удара. Итоговый счет раунда `TotalScore` формируется суммированием `HitScore` всех зарегистрированных нот.

#### 4.7.7. Формула вычисления процента общей точности (Accuracy)

общий процент точности прохождения карты рассчитывается по формуле:

$$Accuracy = \frac{300 \cdot N_{300} + 200 \cdot N_{200} + 100 \cdot N_{100}}{300 \cdot (N_{300} + N_{200} + N_{100} + N_{miss})} \times 100\%$$

где `N_300`, `N_200`, `N_100` — количество попаданий с оценками 300 («Идеально»), 200 («Хорошо»), 100 («Сойдет»); `N_miss` — суммарное количество промахов (включая автопромахи). Точность вычисляется с округлением до сотых долей процента (0.01%).

#### 4.7.8. Динамика шкалы здоровья (HP)

значение HP находится в диапазоне целых чисел от 0 до 100; стартовое значение HP в момент старта игры: 50 единиц; верхняя граница: при восстановлении значение не может превысить 100 единиц (HP = min(100, HP + ΔHP)); нижняя граница: при списании значение не опускается ниже 0 единиц (HP = max(0, HP - 5)).

#### 4.7.9. Условия завершения раунда

**1)** Досрочное поражение (статус «Fail»): наступает немедленно в момент снижения уровня здоровья до 0 (HP <= 0). Воспроизведение музыки останавливается, движение нот прекращается, на экран выводится диалоговое окно «Поражение» с кнопками «Повторить» (перезапуск карты с начала) и «Выход в меню» (возврат в меню выбора карты). Результат сессии со статусом «Fail» не подлежит отправке в таблицу лидеров;

**2)** Успешное завершение (статус «Clear» / Победа): наступает, когда обработаны все ноты карты до конца композиции и значение шкалы здоровья строго больше нуля (HP > 0). Воспроизведение трека завершается, открывается экран результатов.

#### 4.7.10. Градация итоговых рангов мастерства. По итогам раунда со статусом «Clear» игроку присваивается буквенный ранг мастерства:

* Ранг «SS»: Accuracy = 100.00% (при условиях N_200 = 0, N_100 = 0, N_miss = 0);
* Ранг «S»: Accuracy >= 95.00% при условии N_miss = 0;
* Ранг «A»: Accuracy >= 90.00%;
* Ранг «B»: Accuracy >= 80.00%;
* Ранг «C»: Accuracy >= 70.00%;
* Ранг «D»: Accuracy < 70.00%;
* Ранг «FAIL»: присваивается при досрочном поражении игрока при HP <= 0.

#### 4.7.11. Состав экрана результатов. Экран результатов отображает:

* буквенный символ присвоенного ранга (SS, S, A, B, C, D);
* итоговый набранный счет (Total Score);
* общий процент точности (Accuracy);
* максимальную достигнутую непрерывную серию комбо (Max Combo);
* детальную статистику попаданий: количество попаданий «Идеально» (N_300), «Хорошо» (N_200), «Сойдет» (N_100), количество промахов (N_miss);
* кнопку «Повторить» (мгновенный перезапуск карты);
* кнопку «Выход в меню» (возврат в меню выбора карты).

### 4.8. Требования к разделу «Таблица лидеров»

**4.8.1.** Взаимодействие с базой данных Firebase Realtime Database осуществляется по протоколу HTTPS через REST API с использованием формата данных JSON.
**4.8.2.** Все сетевые запросы выполняются в асинхронном неблокирующем режиме средствами класса QNetworkAccessManager с фиксированным таймаутом ожидания ответа 5000 мс.
**4.8.3.** Структура хранения данных в базе данных организована по следующей иерархии: корневой путь `/leaderboards/{map_hash}/{nickname}.json`, где `{map_hash}` — 64-символьная шестнадцатеричная строка хеша карты SHA-256; `{nickname}` — псевдоним игрока длиной от 3 до 20 символов.

**4.8.4.** Каждая запись результата игрока в Firebase Realtime Database содержит девять обязательных полей:
* `nickname` (строка) — псевдоним игрока (от 3 до 20 символов);
* `score` (целое число) — итоговый набранный счет;
* `accuracy` (вещественное число) — процент точности в диапазоне от 0.00 до 100.00;
* `maxCombo` (целое число) — максимальная серия комбо за раунд;
* `count300` (целое число) — количество попаданий «Идеально»;
* `count200` (целое число) — количество попаданий «Хорошо»;
* `count100` (целое число) — количество попаданий «Сойдет»;
* `countMiss` (целое число) — количество промахов;
* `date` (строка) — дата и время фиксации результата в формате ISO-8601 (`YYYY-MM-DDTHH:MM:SSZ`).

Пример JSON-документа рекорда:
```json
{
  "nickname": "Player1",
  "score": 125000,
  "accuracy": 98.50,
  "maxCombo": 120,
  "count300": 95,
  "count200": 10,
  "count100": 2,
  "countMiss": 1,
  "date": "2026-10-17T12:00:00Z"
}
```

#### 4.8.5. Алгоритм загрузки таблицы лидеров

для отображения глобального рейтинга по выбранной карте Система отправляет запрос: `GET /leaderboards/{map_hash}.json?orderBy="score"&limitToLast=10`. Полученные записи сортируются по убыванию значения поля `score` и выводятся в таблице в количестве не более 10 строк с отображением колонок: Место, Имя игрока, Счет, Точность, Макс. комбо, Дата.

#### 4.8.6. Алгоритм отправки рекорда и разрешения коллизий при совпадении псевдонима (ников): отправка рекорда доступна только при успешном завершении раунда (состояние Clear):

**1)** Система выполняет запрос `GET /leaderboards/{map_hash}/{nickname}.json` для получения текущего рекорда игрока с данным псевдонимом;

**2)** если запись для указанного `{nickname}` отсутствует в базе данных, Система отправляет запрос `PUT /leaderboards/{map_hash}/{nickname}.json` с телом новой записи;

**3)** если запись для указанного `{nickname}` уже присутствует в базе данных, Система производит численное сравнение: если новый результат счета строго превышает ранее зафиксированный счет (`new_score > old_score`), Система отправляет запрос `PUT /leaderboards/{map_hash}/{nickname}.json` и перезаписывает запись новыми значениями очков, точности, комбо, попаданий и даты; если новый результат счета меньше либо равен ранее зафиксированному счету (`new_score <= old_score`), перезапись записи в базе данных не производится, в рейтинге сохраняется более высокий счет, а пользователю выводится информационное уведомление: «Рекорд не побит. В рейтинге сохранен текущий лучший результат».

#### 4.8.7. Отказоустойчивость и автономный режим

при отсутствии подключения к сети Интернет, превышении времени ожидания 5000 мс или коде ответа сервера, отличном от HTTP 200 OK, Система выводит в строке статуса сообщение: «Сетевое подключение недоступно. Отображаются локальные результаты». Система сохраняет локальный результат раунда в файл `local_scores.json` и не прерывает работу приложения.

### 4.9. Требование к разделу «Редактор карт»

**4.9.1.** Редактор карт должен предоставлять графическую рабочую область с интерактивным таймлайном звуковой дорожки.

#### 4.9.2. В редакторе должны поддерживаться следующие функции навигации: масштабирование таймлайна (комбинация клавиш Ctrl + колесико мыши), горизонтальная прокрутка, пошаговая перемотка и изменение скорости воспроизведения со значениями 0.25x, 0.5x, 0.75x и 1.0x для точной расстановки нот.

#### 4.9.3. Разметка нот должна поддерживать два режима

1) Режим динамической записи (Tap Record): воспроизведение трека с автоматической расстановкой нот по нажатию клавиш Space или X с квантованием по долям такта; 2) Режим ручного редактирования: добавление ноты кликом левой кнопки мыши на выбранной временной отметке таймлайна, удаление ноты кликом правой кнопки мыши по существующей ноте.
**4.9.4.** В редакторе должны настраиваться параметры карты: темп композиции (BPM) в диапазоне от 30.0 до 300.0, смещение первого такта (audioOffset в мс), сетка квантования с долями 1/1, 1/2, 1/3, 1/4, 1/8, 1/16 такта.
**4.9.5.** Редактор должен включать режим тестового запуска создаваемой карты с текущей позиции курсора воспроизведения без необходимости предварительного сохранения и закрытия редактора.
**4.9.6.** Экспорт созданной карты должен производиться в файл формата .bkey с проверкой корректности структуры данных и упаковкой аудиофайла и файла обложки.

### 4.10. Требования к разделу «Формат файла карты (.bkey)»

Разработчиками спроектирован специализированный формат пакета игровых карт со следующими техническими спецификациями и расширением .bkey:
**4.10.1.** Файл формата .bkey представляет собой контейнерный архив стандарта ZIP без пароля, содержащий в корневой директории строго определенный состав файлов: 1) map.json — текстовый файл манифеста конфигурации карты и временной разметки нот в кодировке UTF-8; 2) файл музыкальной композиции (имя файла совпадает со значением поля audioFileName манифеста, форматы: .mp3, .wav или .ogg); 3) файл графической обложки карты (имя файла совпадает со значением поля coverFileName манифеста, форматы: .png или .jpg, разрешение не менее 400×400 пикселей).

#### 4.10.2. Спецификация файла манифеста map.json

Файл манифеста содержит обязательные поля:
* `formatVersion` (целое число): версия формата карты, фиксированное значение `1`;
* `id` (строка): уникальный идентификатор карты (SHA-256 хеш);
* объект `meta`:
  * `title` (строка, от 1 до 100 символов) — наименование композиции;
  * `artist` (строка, от 1 до 100 символов) — имя исполнителя;
  * `mapper` (строка, от 1 до 50 символов) — псевдоним автора разметки карты;
  * `difficultyName` (строка) — наименование сложности карты;
  * `bpm` (вещественное число) — темп произведения в диапазоне от 30.0 до 300.0 ударов в минуту;
  * `audioOffset` (целое число) — смещение первого такта в миллисекундах;
  * `audioFileName` (строка) — имя аудиофайла внутри архива;
  * `coverFileName` (строка) — имя файла обложки внутри архива;
  * `previewTimeMs` (целое число) — отметка начала предпрослушивания (в мс);
* объект `gameplay`:
  * `scrollSpeed` (вещественное число, диапазон от 0.5 до 3.0, по умолчанию 1.0) — множитель скорости движения нот;
  * `hpDrainRate` (вещественное число, по умолчанию 1.0) — множитель расхода здоровья;
* массив `notes`: упорядоченный по возрастанию список объектов нот:
  * `time` (целое число) — целевое время удара ноты в миллисекундах от старта трека;
  * `type` (строка) — тип ноты, фиксированное значение `"single"`.

Пример файла манифеста `map.json`:
```json
{
  "formatVersion": 1,
  "id": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
  "meta": {
    "title": "Neon Velocity",
    "artist": "Synthwave Collective",
    "mapper": "Gamer_Pro",
    "difficultyName": "Normal",
    "bpm": 128.0,
    "audioOffset": 24,
    "audioFileName": "audio.mp3",
    "coverFileName": "cover.png",
    "previewTimeMs": 30000
  },
  "gameplay": {
    "scrollSpeed": 1.0,
    "hpDrainRate": 1.0
  },
  "notes": [
    { "time": 1000, "type": "single" },
    { "time": 1500, "type": "single" },
    { "time": 2000, "type": "single" },
    { "time": 2500, "type": "single" }
  ]
}
```

#### 4.10.3. Алгоритм идентификации карты (Map Hash)

уникальный идентификатор карты рассчитывается по криптографическому алгоритму SHA-256 от массива байтов файла map.json и аудиофайла карты. Идентификатор представляет собой 64-символьную шестнадцатеричную строку и служит первичным ключом для связывания карты с таблицей лидеров в Firebase Realtime Database. Любая модификация разметки нот или замена аудиофайла приводит к генерации нового хеша и изоляции таблицы лидеров обновленной карты.

#### 4.10.4. Валидация пакета .bkey

при открытии файла карты Система производит автоматическую проверку: 1) целостность архива ZIP; 2) наличие в корне архива файла map.json; 3) синтаксическая корректность JSON и наличие всех обязательных полей; 4) присутствие внутри архива аудиофайла с именем, указанным в поле audioFileName. При обнаружении ошибки Система отклоняет файл с выводом сообщения: «Ошибка валидации карты .bkey: [причина ошибки]» без сбоя в работе приложения.

### 4.11. Требования к разделу «Настройки и калибровка»

Экран «Настройки» должен содержать следующие функциональные блоки:

#### 4.11.1. Блок профиля игрока

текстовое поле ввода «Имя игрока» (псевдоним длиной от 3 до 20 символов);

#### 4.11.2. Блок регулировки громкости

три независимых ползунка с шагом 1% (от 0% до 100%): «Общая громкость», «Громкость музыки», «Громкость звуковых эффектов»;

#### 4.11.3. Блок переназначения клавиш управления

две интерактивные кнопки («Основная клавиша», «Дополнительная клавиша»), которые при нажатии переходят в режим захвата ввода и фиксируют следующую нажатую клавишу клавиатуры (с проверкой: исключается назначение одной клавиши на два действия одновременно, клавиша Escape зарезервирована для системных функций);

#### 4.11.4. Блок калибровки задержки (Audio Offset)

содержит поле ручного ввода смещения в диапазоне от -200 до +200 мс с шагом 1 мс и кнопку «Автоматическая калибровка». При нажатии кнопки «Автоматическая калибровка» Система запускает интерактивный тест: воспроизводится последовательность из 10 звуковых кликов с равным интервалом в 500 мс. При каждом звуковом клике пользователь производит нажатие назначенной игровой клавиши. Система фиксирует временное отклонение $\Delta t_i = t_{press, i} - t_{signal, i}$ для каждого из 10 кликов, вычисляет среднее арифметическое значение:

$$\Delta t_{avg} = \frac{1}{10} \sum_{i=1}^{10} \Delta t_i$$

и автоматически записывает полученную величину в поле Audio Offset;

#### 4.11.5. Блок видеорежима

переключатель между режимами «Полноэкранный режим» (Full Screen) и «Оконный режим» (Windowed с фиксированным разрешением 1920×1080 пикселей);

#### 4.11.6. Кнопка «Сбросить локальные рекорды»

удаляет все записи локальной таблицы лидеров после подтверждения в модальном диалоговом окне;

#### 4.11.7. Кнопка «Сохранить»

сохраняет измененные параметры в файл конфигурации settings.ini и возвращает в Главное меню;

#### 4.11.8. Кнопка «Отмена»

закрывает экран настроек без сохранения изменений и возвращает в Главное меню.

### 4.12. Требования к дизайну приложения

**4.12.1.** Все экраны и диалоговые окна Системы должны быть оформлены в едином графическом стиле с контрастным выделением интерактивных элементов управления.
**4.12.2.** Графические элементы игрового поля (ноты, линия зоны нажатия) должны обладать контрастным цветовым оформлением относительно фонового изображения карты.
**4.12.3.** Анимация движения нот и визуальные эффекты попаданий должны отображаться без рывков с фиксированной частотой не менее 60 кадров/с.
**4.12.4.** Графический интерфейс Системы должен быть оптимизирован под базовое разрешение экрана 1920×1080 пикселей с сохранением пропорций 16:9.
**4.12.5.** Текстовые индикаторы игрового интерфейса (счетчик комбо, текущий счет, процент точности, шкала здоровья) должны сохранять четкую читаемость в процессе воспроизведения карты.

### 4.13. Требования к учету игровой статистики и аналитике

**4.13.1.** Система должна вести учет метрик каждого раунда: общее количество нот на карте, количество попаданий «Идеально» (N_300), «Хорошо» (N_200), «Сойдет» (N_100), число промахов (N_miss), максимальная серия комбо (MaxCombo) и набранные очки (TotalScore).
**4.13.2.** На основе собранных данных по завершении раунда рассчитывается итоговый процент точности Accuracy по формуле п. 4.7.7 настоящего ТЗ.
**4.13.3.** При успешном завершении раунда (статус Clear) Система присваивает игроку буквенный ранг мастерства (SS, S, A, B, C, D) в соответствии с правилами п. 4.7.10 настоящего ТЗ.
**4.13.4.** Система должна сохранять статистику попыток пользователя в локальном файле local_scores.json для отображения в локальной таблице лидеров.

### 4.14. Требования к режимам функционирования, нагрузке и аппаратному обеспечению

**4.14.1.** Система должна функционировать под управлением 64-разрядных операционных систем Microsoft Windows 10 и Microsoft Windows 11.
**4.14.2.** В активном игровом режиме Система должна обеспечивать стабильную частоту смены кадров не менее 60 FPS.

#### 4.14.3. Минимальные системные требования к аппаратному обеспечению

* процессор: двухъядерный процессор Intel Core i3 (не менее 4 вычислительных потоков, базовая тактовая частота не менее 2.0 ГГц) или эквивалентный процессор архитектуры x86-64;
* оперативная память (RAM): объем не менее 8 ГБ;
* видеоадаптер: интегрированный графический адаптер Intel UHD Graphics или дискретный видеоадаптер с аппаратной поддержкой OpenGL 3.3 или DirectX 11;
* свободный объем на накопителе: не менее 500 МБ;
* дисплей: физическое разрешение не менее 1920×1080 пикселей при частоте обновления 60 Гц;
* звуковое устройство: стереофоническая аудиокарта или встроенный звуковой кодек с поддержкой вывода звука через динамики или наушники;
* устройства ввода: аппаратная клавиатура, манипулятор «мышь»;
* сетевой интерфейс: сетевой адаптер Ethernet или Wi-Fi (требуется исключительно для взаимодействия с таблицей лидеров Firebase Realtime Database; в автономном игровом режиме не требуется).
**4.14.4.** Система должна корректно освобождать выделенную память и мультимедийные дескрипторы при закрытии программы или переключении экранов.

### 4.15. Требования по обеспечению информационной безопасности

**4.15.1.** Сетевое взаимодействие между клиентом «BeatKey» и сервером базы данных Firebase Realtime Database должно осуществляться исключительно по защищенному протоколу HTTPS с шифрованием передаваемого трафика.
**4.15.2.** Система должна выполнять строгую проверку типов и диапазонов входных данных, поступающих от пользователя и из файлов карт .bkey, для предотвращения переполнения буфера и сбоев адресации памяти.
**4.15.3.** Все файлы конфигурации (settings.ini), локальные рекорды (local_scores.json) и кэш карт должны сохраняться в штатных пользовательских каталогах операционной системы без требования повышенных административных привилегий.

## 5. Требования к информационному наполнению (материалам)
